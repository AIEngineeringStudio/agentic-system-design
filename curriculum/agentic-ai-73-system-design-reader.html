Worked example: #36 Expense-analysis MCP App

This is a compact worked-design example, not a claim of an already executed code project. It demonstrates how the remaining anchors should be taught.

7.1 Define the problem before the technology

User story: An expense analyst asks an AI assistant: “Show spending by category for Q3; let me adjust the threshold and inspect anomalies.” A prose answer is inadequate because the analyst needs an interactive chart within the conversation.

Functional requirements: Retrieve mock expense data, show summary/charts, adjust a filter locally, optionally request a new tool query, and fall back to text if the host does not support embedded UI. The example uses fake data; it does not initiate payments.

Quality priorities: Correct tenant access > trusted actions > readable UI > interactive latency > deployment simplicity. Example dataset size is small; no large-scale infrastructure is needed yet.

7.2 Introduce exactly the concepts the requirement creates

  • Tool: A typed callable capability, such as get_expense_summary(period, department). The model/host requests it, but the server performs authorization and queries the actual source of truth.
  • MCP: The shared contract that lets a compatible host access the tool without rewriting the same tool integration for each client.
  • MCP App: An optional MCP extension where a tool points to a ui:// HTML resource. A compatible host displays it in a sandboxed iframe and mediates messages through its bridge.
  • UI state: The selected chart filter should live in the view; authoritative permissions and any persisted business change must remain server-side.
  • Host fallback: An ordinary MCP tool result must remain useful if the target host cannot render MCP Apps.

Happy path: User asks → host chooses tool → server validates request and returns data → host fetches the linked UI resource → host displays the HTML view → user adjusts a filter → view updates locally or asks the host to call an app-permitted tool.

7.4 Data and interface contracts

Example logical tool request (not SDK-specific wire syntax):

{"tool": "get_expense_summary", "arguments": {"period": "2026-Q3", "department": "sales"}}

Example tool response shape:

{
  "period": "2026-Q3",
  "currency": "USD",
  "categories": [
    {"name": "Travel", "amount": 1800},
    {"name": "Software", "amount": 650}
  ],
  "as_of": "2026-10-01T00:00:00Z"
}

An implementation should link the tool to a ui:// resource using the MCP Apps specification for the actual SDK version. The payload above is intentionally application-level JSON, not an invented MCP envelope. For practice, implement one tool with summary data and one linked HTML view; test it in a host that explicitly supports MCP Apps.

7.5 Evolve the architecture because of named requirements

1. Requirement — no cross-tenant access. The server derives tenant/user from verified credentials; do not accept tenant choice from the model or iframe as authority.

2. Requirement — unsafe instructions in expense memos. Treat tool/data content as untrusted, not as policy or instructions.

3. Requirement — expensive date-range queries. Use bounded query windows, paging/aggregation and a cache with a visible freshness timestamp.

4. Requirement — host incompatibility. Return human-readable text/structured data; do not assume all MCP clients support MCP Apps.

5. Requirement — operational diagnosis. Trace host request, MCP tool, database query and UI error separately; keep sensitive query values out of logs.

6. Requirement — reproducibility. Version tool input/output schema, UI bundle and SDK/runtime versions.

     No host UI support --> useful text/structured fallback
     Revoked permission --> deny tool call; do not show old data
     Tool timeout       --> error UI + bounded retry, no fake totals

Failure sequence: User's permission is revoked after viewing the dashboard. When they request refreshed values, server authorization must reject the call even if the iframe still contains stale local data. The UI should show the failed refresh; it must not invent a successful result.

7.7 The choice that matters

Option When it fits Trade-off
Plain MCP tool result User only needs text or structured data No rich in-chat control surface
MCP Apps A compatible conversational host should render an inline tool-owned HTML view Optional host support; iframe and bridge security requirements
AG-UI + first-party web app You own the application's frontend and need live agent progress/state You build and operate the web app; a separate concern from MCP tool UI
A2UI A host should render agent-declared components from its own approved catalog Requires compatible renderer and approved component set

Production acceptance criteria: (1) authorized user sees only their own department's sample data, (2) a disallowed tool action is rejected by the server, (3) incompatible host receives usable fallback text, (4) interrupted queries show explicit error, (5) request/trace IDs correlate across the server, (6) UI works without external JavaScript dependencies if building the standalone lab.

Scope note

This is a proposed curriculum, not a certified industry question bank. The catalog has 73 guided briefs and one compact fully worked example, not 73 complete software implementations. You can study cases one by one in depth.

Hands-on checklist for every case

  1. Draw minimal ASCII component diagram.
  2. Describe the data, trust and state boundaries.
  3. Implement one working path with mock data.
  4. Test failure, duplicate, timeout and unauthorized flows.
  5. Draw production diagram and explain trade-offs.
