1. Learning goal and prerequisites

Goal: design and explain robust LangGraph workflows, not only build a chat agent. You should be able to choose when a graph is justified, model typed state, control execution, handle failures, and protect business actions.

Recommended prerequisites: basic Python, functions and dictionaries, type hints, HTTP/API fundamentals, tool calling and structured LLM output. You do not need RAG, MCP, A2A or LangSmith to complete the first labs.

Scope of this guide: LangGraph Python Graph API. The example uses deterministic mock functions, so no paid model or API key is needed. LangGraph implements both workflows and agent loops; it does not require an LLM in every node.

Case study

Build an IT Incident Investigator. An operator submits an alert. The system classifies severity, collects synthetic evidence, recommends a next step, requests approval for a simulated escalation, and keeps enough state to continue later.

ActorResponsibility
OperatorStarts investigation, reviews recommended actions, approves or rejects.
LangGraph runtimeControls steps, routing, state updates and pause/resume.
Monitoring toolsReturn evidence; real source of truth remains the monitoring platform.
Business serviceValidates identity and authorization, and performs real external effects. The model cannot grant these permissions.
CheckpointerStores thread-local execution checkpoints; not a substitute for the business database.

Ranked constraints

  1. Never perform unauthorized or duplicate high-impact operations.
  2. Give traceable evidence and safe stop conditions.
  3. Survive pauses, errors and worker restarts when durable persistence is configured.
  4. Keep latency and tool/token cost bounded.
  5. Make the design testable without depending on model quality.

2. Mental model: graph, state, nodes and edges

LangGraph gives you a graph runtime. Nodes are Python functions that do steps. Edges decide which step runs next. State is shared, typed data passed between steps. Nodes normally return partial updates to state, not a replacement for the entire state.

+------------------------+
| Operator submits alert |
+------------------------+
            |
            v
+------------------------+
| Classify severity      |
+------------------------+
            |
       +----+----+
       |         |
      low       high
       |         |
       v         v
+-------------+ +---------------------+
| Record only | | Investigate metrics |
+-------------+ +---------------------+
       |                |
       |                v
       |       +---------------------+
       |       | Recommend next step |
       |       +---------------------+
       |                |
       +-------+--------+
               v
             [END]

Core vocabulary

TermPractical meaning
StateGraphBuilder that defines state schema, nodes and edges.
TypedDictOne way to declare keys and types of shared state.
START / ENDVirtual entry and terminal graph markers.
NodeA callable that reads state and returns updates.
Normal edgeAlways transitions to a named successor.
Conditional edgeRoutes according to an application decision function.
compile()Builds the executable graph and attaches run-time features such as checkpointing.
invoke()Executes the graph and returns its resulting state/output.
Architecture rule: LangGraph is not itself a business system of record, identity provider, or authorization system. Keep those responsibilities at trusted service boundaries.

3. Lab 1 — Build your first graph

Build a deterministic severity classifier. The goal is to understand routing and state before adding nondeterministic model behavior.

Setup

python -m venv .venv
# Activate your environment (platform-dependent)
python -m pip install -U langgraph
python langgraph_lab_01_routing.py

Save the following as langgraph_lab_01_routing.py (also supplied separately).

"""LangGraph Lab 01: deterministic incident routing; no LLM/API key required.

Install: python -m pip install -U langgraph
Run: python langgraph_lab_01_routing.py
"""
from typing import Literal, TypedDict
from langgraph.graph import START, END, StateGraph


class IncidentState(TypedDict, total=False):
    alert: str
    severity: Literal["low", "high"]
    evidence: list[str]
    recommendation: str


def classify(state: IncidentState) -> dict:
    text = state["alert"].lower()
    severity = "high" if any(x in text for x in ("down", "outage", "payment")) else "low"
    return {"severity": severity}


def route(state: IncidentState) -> Literal["high", "low"]:
    return state["severity"]


def investigate(state: IncidentState) -> dict:
    return {"evidence": ["mock-metrics: 5xx rate increased", "mock-logs: 504 spike"]}


def recommend(state: IncidentState) -> dict:
    return {"recommendation": "Escalate for on-call review; no action executed."}


def close_low(state: IncidentState) -> dict:
    return {"recommendation": "Record and monitor; no action executed."}


builder = StateGraph(IncidentState)
builder.add_node("classify", classify)
builder.add_node("investigate", investigate)
builder.add_node("recommend", recommend)
builder.add_node("close_low", close_low)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route, {"high": "investigate", "low": "close_low"})
builder.add_edge("investigate", "recommend")
builder.add_edge("recommend", END)
builder.add_edge("close_low", END)
app = builder.compile()

if __name__ == "__main__":
    for alert in ("Payments down in west region", "Disk usage 65 percent"):
        result = app.invoke({"alert": alert})
        print(result)

Inputs and expected behavior

InputExpected routeExpected result
Payments down in west regionhigh → investigate → recommendMock evidence and escalation recommendation
Disk usage 65 percentlow → close_lowMonitoring recommendation; no evidence retrieval

Inspect: The state update from classify becomes the input of the routing function. The routing function should be deterministic and total (every permitted value has a destination).

Failure exercise: Remove a destination from the routing map and inspect the error. Then add a fallback branch that marks an unknown alert for manual triage.

4. State design and reducers

Design state around the business process. Store raw durable facts and step results, not large formatted prompts. A state key with no reducer normally uses last-write/overwrite behavior. A reducer defines how multiple updates combine, which is important for parallel branches.

Simple schema

from typing import Annotated, TypedDict
import operator

class InvestigationState(TypedDict, total=False):
    incident_id: str
    user_request: str
    status: str
    evidence: Annotated[list[str], operator.add]
    final_report: str

evidence uses an append-style reducer. If two workers return {"evidence": ["metric-1"]} and {"evidence": ["log-2"]}, both results can be merged. Without an appropriate reducer, simultaneous writes to one state key can conflict.

Important: do not use append reducers for values that must be replaced or cleared. The order of parallel results is not a good foundation for business meaning. Use stable IDs and deterministic ordering when needed.

State ownership rules

  1. Graph state: facts needed by upcoming workflow steps.
  2. Checkpointer: thread-scoped snapshots of graph state.
  3. Store: long-term, cross-thread application memory if required.
  4. Business database: source-of-truth incident records, approvals, action IDs, audit log.
  5. Runtime context: trusted dependencies and service configuration, not user-editable instructions.

For chat-centric agents, MessagesState includes message-specific update semantics. For an incident workflow, a typed business state is usually easier to inspect than storing everything in a single message list.

5. Dynamic control flow and agents

A workflow has mostly predefined steps. An agent chooses tools or actions dynamically based on state and model output. Both can run on LangGraph.

PatternWhen to useMain risk
Linear sequenceExtract → validate → summarizeToo rigid for unexpected inputs
RouterLow/medium/high severity or task categoryWrong route or missing fallback
Bounded tool loopAgent needs iterative tool selectionInfinite tool calls and runaway cost
Planner → executorMulti-step research that can be re-plannedUnnecessary planning overhead
Supervisor → specialistDifferent skills/tools and clear subtasksComplicated handoffs and conflicting findings

Minimum agent loop: model proposes a structured tool call → application validates tool/arguments/rights → tool executes → result is returned as data → loop repeats with an iteration limit → final answer. LangGraph provides orchestration but does not authorize the tool call.

+---------------------+
| Agent / model step  |
+---------------------+
          |
          v
+---------------------+
| Tool needed?        |
+---------------------+
       |        |
      no       yes
       |        |
       v        v
     [END] +---------------------+
           | Validate tool call  |
           +---------------------+
                    |
                    v
           +---------------------+
           | Execute bounded tool|
           +---------------------+
                    |
                    +-------> Agent / model step

Useful LangGraph controls include add_conditional_edges, Command(update=..., goto=...) for combined state update and routing, and Send for dynamic fan-out.

Decision rule

If business logic fully determines the next step, use ordinary Python or deterministic graph nodes. Introduce an LLM-driven decision only where text understanding, interpretation, or flexible tool selection adds measurable value.

6. Persistence, threads, memory and replay

A thread identifies a continuing workflow or conversation. Attach a checkpointer to persist snapshots and pass the same thread_id to continue or inspect it. A store is different: it is for data shared across runs/threads.

Basic checkpoint setup

from langgraph.checkpoint.memory import InMemorySaver

app = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "incident-42"}}
result = app.invoke({"incident_id": "INC-42"}, config=config)
snapshot = app.get_state(config)
print(snapshot.values)

InMemorySaver is only for local development. It does not survive process exit. Use a persistent checkpointer backend when restart recovery is a requirement. Account for checkpoint storage, cleanup, schema migrations, encryption and tenant isolation.

FeatureMeaning
CheckpointSaved graph state at an execution boundary.
ThreadIdentity that groups a continuing run/conversation.
ResumeContinue after pause/failure using the same thread identity.
State historyInspect earlier snapshots to debug a run.
Time travelReplay or fork from a past checkpoint for investigation.
StoreCross-thread memory such as approved user preferences.
Crucial distinction: checkpoint persistence does not guarantee exactly-once external side effects. A remote provider may complete a write and then lose the response. Your business service must use idempotency and reconciliation.

"""LangGraph Lab 02: interrupt/resume with a fake, non-writing action.

Install: python -m pip install -U langgraph
Run: python langgraph_lab_02_approval.py

Important: InMemorySaver is not durable across process restarts. The caller's
approval must be authenticated and authorized by a separate business service.
"""
from typing import Literal, TypedDict
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, END, StateGraph
from langgraph.types import Command, interrupt


class ApprovalState(TypedDict, total=False):
    incident_id: str
    proposed_action: str
    decision: Literal["approved", "rejected"]
    result: str


def prepare(state: ApprovalState) -> dict:
    return {"proposed_action": "Create a mock on-call escalation"}


def review(state: ApprovalState) -> dict:
    approved = interrupt({
        "incident_id": state["incident_id"],
        "proposed_action": state["proposed_action"],
        "question": "Approve this simulated escalation?",
    })
    return {"decision": "approved" if approved is True else "rejected"}


def route(state: ApprovalState) -> Literal["approved", "rejected"]:
    return state["decision"]


def simulate_action(state: ApprovalState) -> dict:
    # This is only a local mock. No email/API/database write is made.
    return {"result": "SIMULATED: escalation would be created"}


def cancel(state: ApprovalState) -> dict:
    return {"result": "Rejected: no escalation created"}


builder = StateGraph(ApprovalState)
builder.add_node("prepare", prepare)
builder.add_node("review", review)
builder.add_node("simulate_action", simulate_action)
builder.add_node("cancel", cancel)
builder.add_edge(START, "prepare")
builder.add_edge("prepare", "review")
builder.add_conditional_edges("review", route, {
    "approved": "simulate_action", "rejected": "cancel"
})
builder.add_edge("simulate_action", END)
builder.add_edge("cancel", END)
app = builder.compile(checkpointer=InMemorySaver())

if __name__ == "__main__":
    config = {"configurable": {"thread_id": "demo-incident-42"}}
    first = app.invoke({"incident_id": "INC-42"}, config=config)
    print("Paused:", first.get("__interrupt__"))
    final = app.invoke(Command(resume=True), config=config)
    print("Final:", final)

What happens

  1. First invoke() reaches the review node and returns an interrupt payload.
  2. The caller displays the proposal and obtains a decision.
  3. The caller resumes using Command(resume=True) and the same thread ID.
  4. The graph takes the approved/rejected branch.
Replay trap: an interrupted node starts again from the beginning when resumed. Avoid non-idempotent external writes before interrupt(). For real approval, verify the authenticated reviewer, the exact action, authorization policy, and expiration on the backend.

8. Parallelism, subgraphs and streaming

Fan-out / fan-in

For an incident, log analysis, metrics analysis and deployment-change analysis can run as independent branches. Combine results with typed reducers, then synthesize findings. Use Send when the number of worker tasks is determined at runtime.

               +------------------+
               | Plan investigation|
               +------------------+
                         |
               +---------+---------+
               |         |         |
               v         v         v
         +----------+ +---------+ +----------+
         | Log scan | | Metrics | | Changes  |
         +----------+ +---------+ +----------+
               |         |         |
               +---------+---------+
                         |
                         v
               +------------------+
               | Merge evidence   |
               +------------------+

Subgraphs let a team create a graph that runs inside another graph. This is useful for reusable investigation units, or separately owned workflow parts. Do not equate an in-process subgraph with a remote A2A agent.

Streaming choices

MechanismUse
invokeReturn final result for a short operation.
stream(..., stream_mode=...)Inspect low-level step updates, state values or messages.
stream_events(..., version="v3")Newer typed-projection interface for messages, values, interrupts and output.
Web SSE / frontend adapterSend server-approved progress information to a browser; LangGraph events are not themselves a complete browser authorization layer.

The official documentation now recommends event streaming for new applications on compatible LangGraph versions; older examples use stream_mode. Version-pin and test the selected API.

9. Reliability and error handling

Choose recovery based on the type of error. Do not handle every failure by asking the model to try again.

FailureApproachEvidence to capture
Temporary tool timeoutBounded retry with backoff and timeoutAttempt count, tool ID, latency
Invalid model outputSchema validation, bounded repair or rejectInvalid field and model version
Missing inputInterrupt or return typed request for clarificationPending question and thread ID
Process restartPersistent checkpoint plus safe resumeCheckpoint ID and restored state
External write outcome unknownStable operation ID; reconcile provider state before retryOperation ID and provider result
Unauthorized tool requestBusiness-service authorization deny; no retry with greater rightsPolicy decision and audit event

12. Architecture decision guide

QuestionChoose this when...
Plain Python or LangGraph?Use plain Python for short, fixed operations without pause/resume/state-history needs. Use LangGraph when explicit graph control or durable workflow features matter.
Graph API or Functional API?Use Graph API for new explicit graphs. Functional API fits wrapping existing functions/frameworks into LangGraph runtime features.
Graph node or tool?Node defines workflow logic; tool defines a callable capability. A node may call a tool, but a tool should still validate inputs and authorize data/effects.
Reducer or overwrite?Reducer for intentional accumulation and concurrent writes; overwrite for single latest truth.
Checkpoint or long-term store?Checkpoint for thread execution continuity; store for cross-thread durable memory. Neither overrides business system authority.
Single agent or multiple specialists?Prefer single bounded agent until independent tools/skills and measured quality justify specialists.
Direct API or MCP?A direct typed API is often simplest for one internal integration. MCP is useful for reusable tool interoperability across host clients.
Subgraph or A2A?Subgraph for locally composed workflow units. A2A for independent remote agent service boundaries.
LangGraph stream or AG-UI?LangGraph emits runtime streams; AG-UI standardizes an agent-to-first-party-frontend protocol. An adapter may bridge them, but they are not the same thing.

Common mistakes to avoid

  1. Using a graph only because AI is involved.
  2. Putting secrets or authorization decisions in prompt/state instead of trusted services.
  3. Assuming thread_id is proof of a user's identity.
  4. Writing to external systems before an interrupt without replay protection.
  5. Keeping huge raw documents or formatted prompts in state.
  6. Using append reducers everywhere, leading to duplicated or unbounded state.
  7. Running infinite agent loops without budgets or explicit stop conditions.
  8. Using in-memory checkpoints as if they survive crashes.
  9. Assuming a successful model response proves a business action succeeded.
  10. Measuring only latency and tokens, not end-to-end task correctness.
