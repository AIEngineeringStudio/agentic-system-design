ROUTE

What we have built so far

We are not designing the entire enterprise platform in one step. Each stage adds only the capabilities justified by INC-42. The platform-wide concerns remain future work.

Stage 1Problem, actors, priorities and trust boundaries
Stage 2LLMs, workflows, tool calling and grounding
Stage 3Two-tool read-only system and typed contracts
Stage 4Runnable synthetic Python workflow and tests
Stage 5ABounded model tool selection and enforcement
Central lessonThe LLM may explain evidence and propose what to inspect next. Application code and business systems decide what data can be read and what actions can run. No production write action exists in our current design.

Business outcome

Reduce investigation effort and help authorized engineers reach safer decisions using verifiable evidence.

Current architectural limit

One bounded incident investigator, two read-only tools, synthetic records, an optional model adapter, and no enterprise-scale platform services.

STAGE 1

Problem definition and requirements

1.1 The incident

Customers experience slow checkouts. Monitoring reports a p95 latency rise from 240 ms to 1,800 ms, while error rate rises from 0.4% to 3.1%. Deployment v2.7.4 occurred at 09:55, shortly before the degradation. All values and identifiers are fictional.

Do not confuse correlation with causeA deployment near the incident is a lead for investigation, not proof that the deployment caused the slowdown.

1.2 Actors and authority

ActorJobAuthority boundary
On-call engineerInvestigate INC-42 and review results.May read only permitted service records.
Incident commanderCoordinate incident response.Controls incident process within assigned rights.
Service owner / SREInterpret technical state and evaluate changes.Can operate only owned/authorized services.
Change approverReview production changes.Approval requires business-side policy enforcement.
Security / platform teamsProvide identity, policies and shared standards.Govern controls; do not replace source-system ownership.

1.3 Representative user journey

1
Engineer asks: “Investigate INC-42. Why is Checkout API slow?”
2
Application authenticates the engineer and checks incident access.
3
Approved tools retrieve metrics and deployment history.
4
Analysis separates observations, hypotheses and unknowns.
5
Engineer reviews the recommendation. No remediation is executed.

1.4 Prioritized functional requirements

PriorityRequirementsArchitectural significance
P0Identify incident; read approved metrics and changes; produce cited findings; recommend without acting; enforce user-specific access.Needs secure input handling, tool interfaces, source provenance and a strict read-only boundary.
P1Handle incomplete/contradictory evidence; show useful timeline/report.Needs explicit failure states, uncertainty and inspectable events.
P2Reuse capabilities across products; add human-approved remediation later.May justify MCP, shared governance, durable workflow and action policy in future increments.

1.5 Ranked non-functional constraints

RankConstraintWhy first?
1Identity and authorizationOperational evidence can be sensitive or tenant-scoped.
2Safe behavior: zero initial writesUnsafe remediation can worsen the incident.
3Evidence correctnessA plausible answer without valid evidence is not reliable.
4Reliability and responsivenessTool failures must not create invented answers.
5Auditability and bounded costOperators need traceable, predictable execution.

Illustrative future target: a usable initial summary within 30 seconds for 95% of requests. This was a proposed learning target, not a measured or agreed enterprise SLO.

Data or decisionSource of truth / ownerAssistant role

DeploymentsChange/deployment serviceRead recent changes; do not infer causality automatically.
Incident statusIncident-management systemRead state; never silently rewrite it.

Included initially

  • One incident and one primary engineer
  • Metrics + deployment reads
  • Evidence-based recommendations
  • Synthetic fixtures and a local mock

Explicitly excluded

  • Automatic rollback/restart
  • Live credentials and production systems
  • Mandatory MCP, RAG or A2A
  • Multi-region scale and shared platform rollout
STAGE 2

Essential AI architecture concepts

Introduce a concept only when it helps solve INC-42. A more advanced technology is not automatically a better design.

ConceptSimple definitionApplied to INC-42
LLMGenerates explanations or structured text from its input.Summarizes why latency may have increased; does not know live metrics without supplied evidence.
Fixed workflowApplication code determines the order of steps.Always read metrics and deployments, then analyze results.
Bounded agentModel helps choose from permitted tools under execution limits.Can propose which diagnostic read to make; cannot invent permissions.
Tool callingModel proposes a typed operation; application validates and runs it.get_metrics and get_deployments are approved reads.
Context engineeringSelect information and instructions relevant to the current model call.Give incident ID, approved evidence, source IDs, and uncertainty rules.
GroundingBase material claims on retrieved records.“Latency is 1,800 ms” cites METRIC-07.
RAGRetrieve relevant knowledge passages before generation.Useful later for large runbook or historical incident collections; unnecessary for two direct structured reads.
Control planeGovernance/configuration of capabilities.Approved tools, tool versions, identity policy and budgets.
Runtime/data planeActual work performed on requests.Incident workflow, authorized tool reads, and report generation.
ObservabilityExplains what executed, where, and with what latency/errors.Shows tool timeline, failures and run correlation.
EvaluationTests whether the output is correct and useful.Checks claims, citations, uncertainty and recommendation safety.

2.2 Facts, hypotheses and missing information

TypeExampleEvidence rule
Observed factp95 latency is 1,800 ms.Cite METRIC-07.
Observed factv2.7.4 deployed at 09:55.Cite CHANGE-03.
HypothesisThe deployment might contribute to degradation.Use both observations; say unverified.
UnknownWhether database saturation caused slow requests.Do not manufacture database metrics.
Key distinctionObservability answers “What happened during the run?” Evaluation answers “Was the investigation answer actually correct?” A successful API response can still contain a wrong analysis.
Why MCP, A2A and GenUI are not required yet

MCP becomes valuable when tools/resources need a reusable host-to-server interface. A2A is useful for delegating work between independently deployed agents. AG-UI streams agent state to owned frontends; A2UI specifies trusted components declaratively; MCP Apps embeds UI in a compatible host. These are separate boundaries, not substitutes for one another.

Our current scope has one application and two simple read functions. Ordinary Python functions and a basic report are sufficient.

3.2 Minimal typed contracts (examples only)

No full implementation code is included. These small JSON examples show the contracts.

Investigation request

{
  "incident_id": "INC-42",
  "service": "checkout-api",
  "question": "Why is it slow?"
}

Metrics tool result

{
  "evidence_id": "METRIC-07",
  "p95_latency_ms": 1800,
  "baseline_p95_ms": 240,
  "error_rate_percent": 3.1
}

Deployment tool result

{
  "evidence_id": "CHANGE-03",
  "version": "v2.7.4",
  "deployed_at": "09:55"
}

Investigation outcome

{
  "status": "needs_review",
  "evidence_ids": [
    "METRIC-07", "CHANGE-03"
  ],
  "action_executed": false
}
Trust the server, not request fieldsThe backend derives principal, tenant and allowed incident scope from verified context. The user’s request and the model do not provide authoritative identity or permissions.

3.3 Happy-path sequence

  1. Validate incident ID and verify engineer access.
  2. Call monitoring tool with trusted principal and service scope.
  3. Call deployment tool under the same source-specific authorization checks.
  4. Build context with retrieved evidence and provenance.
  5. Analyze observations and possible causes.
  6. Validate response shape and referenced evidence IDs.
  7. Return needs_review; no production action.

3.4 Important failure path: metrics timeout

+---------------------------+
| get_metrics: TIMEOUT      |
+---------------------------+
             |
             v
+---------------------------+
| get_deployments: SUCCESS  |
| CHANGE-03 available       |
+---------------------------+
             |
             v
+---------------------------+
| Insufficient evidence     |
| No causal conclusion      |
+---------------------------+

Expected status: insufficient_evidence, with missing_evidence: ["metrics"] and no supported root-cause claim. An authorization failure is different: stop before exposing protected evidence.

4.4 What Stage 4 did not prove

  • Not a real LLM: MockAnalyst generated deterministic results.
  • Not real login: the --user flag selected a synthetic fixture.
  • Not semantic fact verification: matching evidence IDs does not prove the claim’s truth.
  • Not MCP/A2A: tools were Python calls; optional specialist was plain HTTP JSON.
  • Not enterprise availability: no persistent audit, traffic management, or disaster recovery.
STAGE 5A

Evolution 1: Bounded model tool calling

We evolve the baseline only where a new requirement justifies the change: the next diagnostic read may depend on what the incident needs. The model can propose tools, but never execute arbitrary operations.

5.1 Requirement → baseline gap → change → check → trade-off

Design stepEvolution 1 decision
New requirementPermit model-driven selection of approved diagnostic reads.
Baseline gapStage 4 always used the same two tools; analysis was deterministic.
Architecture changeAdd a bounded agent controller and optional real-model provider. All tool calls pass an application allowlist and incident-scope authorization.
Operational checkReject unknown tools, unexpected arguments, duplicate/excessive calls and unsupported evidence IDs.
Trade-offMore flexibility and model cost/uncertainty; less freedom than an unbounded autonomous agent.

5.3 Tool contract: model supplies no scope fields

Permitted proposal

{
  "name": "get_metrics",
  "arguments": {}
}

Rejected proposal

{
  "name": "restart_service",
  "arguments": {
    "service": "checkout-api"
  }
}

The service and tenant are derived from the verified incident registry. The model is not permitted to supply user_id, tenant_id or another target service. The tools themselves repeat authorization checks.

5.4 Hard limits in Evolution 1

ControlBounded policySafety effect
Allowlistget_metrics and get_deployments onlyUnknown or write tools are rejected.
Argument schemaEmpty JSON object {}Model cannot change incident scope.
Call budgetMaximum two distinct tool calls per runLimits repeated or unbounded execution.
Batch validationValidate proposed calls before executing anyA bad proposal cannot partially execute first.
Missing mandatory evidenceinsufficient_evidenceSkip or timeout does not become a root-cause claim.
Report validationCheck structure and returned evidence IDsReject fabricated references.
Remediation toolsNoneCannot restart or roll back through this interface.

5.5 Rejection path: a model requests restart

+----------------------------+
| Model proposes restart     |
+----------------------------+

              v

+----------------------------+
              |
              v
+----------------------------+

| No source/write call made  |

Model output is not authorizationA system prompt saying “do not restart” is useful guidance, but the actual safety control is the application’s deny-by-default dispatch logic and absence of write tools.

5.6 Optional model adapter and verification status

The Stage 5A study implementation included an optional OpenAI Responses API adapter. It used a model request to propose tool calls, then a structured analysis request supplied with the actual results. Tool results were correlated to proposed calls using their call_id. This was not a fully iterative tool-selection loop.

Locally exercised

Scripted model proposals; two-tool dispatch; access-denial and timeout branches; offline adapter parsing/format tests; citation rejection.

Not exercised

Live hosted-model calls, real identity provider, production authorization, semantic factual verification, rate limiting and real incident remediation.

Verification record from the Stage 5A lessonTwenty-three automated tests were reported passing, including prior Stage 4 regression tests and new controller/adapter cases. The live model integration was not executed or model-compatibility-verified in that session.

5.7 Stage 5A design judgment

Keep the deterministic workflow for known, predictable steps. Use bounded model-proposed tool selection when adaptive diagnostics provide real value. Never let the model choose an arbitrary target service, grant itself access, or execute a production write.

Glossary and source map

Evidence IDStable reference to a record retrieved from an approved source.
GroundingSupporting generated claims with retrieved evidence.
Authorization (AuthZ)Decision that a verified actor may perform a specified operation on a resource.
Tool allowlistExplicit set of permitted executable operations.
Tool budgetLimit on number or cost of tool calls during one run.
Structured outputModel response shaped according to a defined schema.
Trust boundaryPoint where input/data crosses into a system with different authority.
