1. New requirement: Adaptive investigation

In Stage 4, we built a working investigation simulator for INC-42.

Evolution 1: Real model reasoning and safe tool execution Now we will improve it one requirement at a time.

An engineer asks:

Investigate INC-42. Checkout API latency increased after deployment. Find the likely cause.

In Stage 4, Python always executed the same two tool calls, then generated a deterministic summary.

That works for predictable incidents. However, future investigations may need different evidence depending on the symptoms.

New requirement: Allow an LLM to choose approved diagnostic tools and analyze their results, without granting it operational authority.

Stage 4Stage 5 — Evolution 1
Tool selectionFixed Python sequenceModel proposes approved tool calls
AnalysisDeterministic mockOptional real LLM
Tool executionApplication controlledStill application controlled
PermissionsSynthetic authorizationSame boundaries, with stronger validation
Production changesNot allowedStill not allowed

The critical principle remains:

The model decides what to request. The application decides what is permitted and executed.

The controller manages the loop. It may return evidence to the model for another decision, but it stops when the request is complete or a defined budget is reached.

This follows the official tool-calling pattern: a model returns a function-call request, application code executes it, and the result is passed back to the model.

Important design decision

We will not expose a tool such as restart_service or rollback_deployment to this investigation agent.

Without those capabilities, the model cannot execute remediation through the approved tool interface, even if it requests it.

This is a stronger boundary than relying only on prompt instructions.

3. The new tool execution contract

For this increment, we deliberately give both tools zero model-supplied arguments.

{
  "name": "get_metrics",
  "arguments": {}
}

The server derives the service and tenant from the already-authorized incident.

This prevents the model from choosing an unrelated service by supplying another service ID.

The application also checks the tool name, argument structure, duplicate calls and maximum call count before executing anything.

7. Next production requirement

We have improved the behavior of one investigation assistant. However, we still have ordinary Python tools tightly coupled to that application.

Imagine three teams:

  • IT Operations wants to investigate incidents.
  • Security Operations wants to inspect service alerts.
  • Platform Engineering wants to inspect deployment health.

All three need some of the same monitoring capabilities.

Duplicating these integrations creates maintenance and governance problems.

This gives us the next architectural question:

Should each AI application own its monitoring integrations, or should we expose approved tools through a shared interface?

That is where we will evaluate MCP against direct APIs.

5.3 Tool request contract: no model-provided scope

Allowed tool names:

  • get_metrics
  • get_deployments

Their model-facing arguments are intentionally empty:

{
  "name": "get_metrics",
  "arguments": {}
}

Why empty arguments? The controller gets the service and tenant from the incident already authorized by application code. The model cannot override them with payroll-api, a different tenant, or a guessed user identity.

Example rejected request:

{
  "name": "get_metrics",
  "arguments": {
    "service": "payroll-api"
  }
}

The controller rejects this because unexpected arguments are not allowed.

5.4 Controller policy

GuardStage 5 Evolution 1 behavior
Tool allowlistOnly the two named read-only tools
ArgumentsEmpty JSON object only
Call budgetAt most two distinct tool calls per request
Duplicate names / IDsReject proposed batch
AuthorizationIncident-scoped at API and source-tool boundaries
Missing tool resultReturn incomplete-evidence status
Unknown toolReject before executing any tool
Model-generated evidence IDsValidate against retrieved records
Remediation toolsNone registered

The proposed batch is validated before any tool executes. This prevents partially executing a batch that also contains a prohibited action.

Conceptual controller logic:

ALLOWED_TOOLS = {"get_metrics", "get_deployments"}
MAX_TOOL_CALLS = 2


def validate_requests(requests):
    if len(requests) > MAX_TOOL_CALLS:
        raise RejectedToolRequest("TOOL_BUDGET_EXCEEDED")

    seen_names = set()
    seen_ids = set()
    for request in requests:
        if request.name not in ALLOWED_TOOLS:
            raise RejectedToolRequest("UNKNOWN_TOOL")
        if request.arguments != {}:
            raise RejectedToolRequest("UNEXPECTED_ARGUMENTS")
        if request.name in seen_names or request.call_id in seen_ids:
            raise RejectedToolRequest("DUPLICATE_TOOL_REQUEST")
        seen_names.add(request.name)
        seen_ids.add(request.call_id)

This excerpt illustrates the contract; the earlier Stage 5A project contained the full implementation and additional input-type checks.

5.5 Model/tool request flow

The Stage 5A adapter uses two model phases:

  1. Ask the model to propose up to two approved read-only tool calls.
  2. After application-side validation and tool execution, supply matching tool outputs and request a structured investigation report.

An actual tool-call response includes a call identifier. The application pairs the result with that identifier when returning the tool output to the model.

Conceptual tool response handed back to the model:

{
  "type": "function_call_output",
  "call_id": "call-01",
  "output": "{\"evidence_id\":\"METRIC-07\",\"p95_latency_ms\":1800}"
}

The model does not directly invoke Python functions. The controller executes the authorized function and supplies its output.

Important limitation: The Stage 5A adapter demonstrated one proposal phase plus one analysis phase, not an unlimited autonomous agent loop. A full iterative tool-selection loop was explicitly deferred.

Prompt instructions such as “do not restart services” are useful defense-in-depth, but the absence of a registered write capability and independent tool validation are the stronger controls.

5.7 Failure scenario: missing evidence

If the model skips get_metrics or monitoring times out:

  1. The controller records metrics as missing.
  2. Other authorized evidence can still be used.
  3. The resulting status is insufficient_evidence.
  4. A deployment-related hypothesis is not treated as confirmed root cause.
  5. No production write is possible.

A denied user is handled earlier: no protected evidence should be retrieved and no unnecessary model request should occur.

What is still missing for production?

  • Real authentication, delegated identity, and service-level authorization tokens.
  • Semantic verification that cited evidence actually supports each claim.
  • Persistent, protected audit records and distributed tracing.
  • Tool timeouts, retry policies, cancellation, and resource quotas for real infrastructure.
  • Version-pinned models, evaluation datasets, rollout gates, and cost budgets.
  • Data classification, retention, and privacy review before sending real operational evidence to a hosted model.
  • Durable approval workflows if future phases add write actions.
  • Shared MCP integration, RAG, AG-UI/A2UI/MCP Apps, or A2A only when a concrete requirement warrants them.

Stage 5 Evolution 1 result

The model can propose approved evidence reads. The application still owns execution and permissions. Reports are checked for structure and existing evidence IDs. All available operational tools remain read-only.

Reusable principles established

  1. Source of truth: The monitoring and deployment systems own business facts.
  2. Trust boundary: The model is not the authorizer and retrieved records are not instructions.
  3. Least privilege: Initial tools read only the specific incident's authorized service.
  4. Evidence: Separate observed measurements, hypotheses, and unknowns.
  5. Failure honesty: Missing evidence must produce an incomplete response, not a confident diagnosis.
  6. Bounded execution: Tool allowlists, argument schemas, and budgets are application controls.
  7. Incremental complexity: Add protocols and distributed services only when justified by requirements.

Glossary and source map

  • p95 latency — 95th percentile of request latency; 95% of measured requests are at or below this value.
  • Evidence ID — Stable reference to a record retrieved from an approved source.
  • Grounding — Supporting generated claims with retrieved evidence.
  • Authorization (AuthZ) — Decision that a verified actor may perform a specified operation on a resource.
  • Tool allowlist — Explicit set of permitted executable operations.
  • Tool budget — Limit on number or cost of tool calls during one run.
  • Structured output — Model response shaped according to a defined schema.
  • Trust boundary — Point where input/data crosses into a system with different authority.
  • MCP — Tool/data interoperability boundary between compatible AI host clients and servers.
  • A2A — Agent-to-agent communication across independently operating services.
  • AG-UI — Agent-to-frontend run/event protocol, distinct from MCP tool transport.
  • Idempotency — Property that retrying the same logical action does not create duplicate effects; needed when writes arrive later.
