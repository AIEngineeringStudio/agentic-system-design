1. Our starting problem

The on-call engineer asks:

Investigate INC-42. Why is Checkout API slow, and what should I do next?

We already have two pieces of synthetic evidence:

EvidenceObservation
METRIC-07p95 latency increased from 240 ms to 1,800 ms
CHANGE-03Version v2.7.4 deployed shortly before the slowdown

A normal application can retrieve these facts. But we want an assistant that can interpret them, explain possible causes, and recommend further investigation.

That distinction introduces our first concept.

2. LLM versus AI agent

What is an LLM?

A Large Language Model (LLM) processes input and generates output, such as explanations, summaries, or structured text.

For example, provide the following evidence:

Checkout API latency: 1,800 ms
Normal latency: 240 ms
Recent deployment: v2.7.4

The model might respond:

Checkout API latency is significantly higher than normal. The recent deployment may be related, but further evidence is needed.

It can explain metrics or summarize a deployment record, but it does not automatically know the current state of Checkout API.

It cannot investigate any system itself.

What is an AI agent?

An AI agent is an application that lets a model participate in deciding which tools or steps to request while pursuing a goal.

The application still executes and authorizes those steps.

For example, the agent may decide to inspect deployment history after detecting a latency spike.

DECISION A: Do we need an agent immediately?

Not necessarily.

Our first investigation has two known data sources and a predictable sequence.

A fixed workflow can fetch those records before passing the evidence to an LLM.

ApproachBest when
Single LLM callAll necessary evidence is already provided
Fixed workflow + LLMRequired evidence sources and steps are known
Bounded agentThe next diagnostic step depends on earlier findings

Initial choice: Start with a fixed, read-only investigation workflow. Introduce adaptive agent behavior when the incident requires it.

This avoids unnecessary model decisions and makes failures easier to understand.

3. Tool calling — how AI accesses operational data

An LLM does not automatically know the current state of Checkout API. It needs a way to obtain data from the systems that own that information.

A tool is an approved operation that the application can execute.

For our incident, we need two read-only tools:

ToolPurpose
get_metricsRetrieve latency and error measurements
get_deploymentsRetrieve recent deployments

Example: tool request and response

The following is a conceptual tool request, not a specific SDK format.

TOOL REQUEST

{
  "tool": "get_metrics",
  "arguments": {
    "service": "checkout-api",
    "incident_id": "INC-42"
  }
}

TOOL RESPONSE — SYNTHETIC DATA

{
  "evidence_id": "METRIC-07",
  "service": "checkout-api",
  "p95_latency_ms": 1800,
  "baseline_p95_ms": 240,
  "error_rate_percent": 3.1
}

The application executes the tool against an approved data source. The model can then interpret the returned evidence.

4. Context engineering and grounding

These concepts solve two related problems.

Context engineering means selecting the information that the model receives for its current task.

Grounding means making important claims depend on actual evidence rather than unsupported model output.

For INC-42, context might contain:

Incident: INC-42
Service: checkout-api

Evidence:
  METRIC-07: p95 latency = 1,800 ms
  CHANGE-03: deployment v2.7.4 at 09:55

Rules:
  Distinguish observations from hypotheses.
  Cite evidence IDs.
  Do not claim root cause without proof.
  Do not execute remediation.

4.1 Facts, hypotheses and missing information

The model should produce something like:

TypeExampleEvidence rule
Observed factLatency increased significantly(p95 latency is 1,800 ms).Cite METRIC-07.
Observed factA deployment v2.7.4 before degradation(at 09:55).Cite CHANGE-03.
HypothesisThe deployment may have contributed to degradation.Use both observations; say unverified.
UnknownWhether database saturation caused slow requests.Do not manufacture database metrics.

Without grounding, the model might confidently declare the deployment responsible, even though another issue caused the slowdown.

Also, evidence retrieved from logs or documents must be treated as data, not instructions. A log entry cannot authorize the assistant to change production.

DECISION B: Do we need RAG?

Not yet.

Retrieval-Augmented Generation (RAG) becomes useful when the assistant needs to search a large collection of runbooks, incident reports or engineering documents.

For our first version, the data is structured and comes from two direct tool calls. A vector database is unnecessary.

5. Control plane versus data plane

This distinction becomes especially important when we evolve the assistant into an enterprise platform.

A control plane governs how capabilities are configured and used.

A data plane, or runtime plane, carries out actual requests and tool operations.

TWO DIFFERENT RESPONSIBILITIES

+──────────────────────────────+
│         CONTROL PLANE        │
│                              │
│ Approved tools and policies  │
│ Configuration and ownership  │
+──────────────────────────────+
               │
               │ Govern
               v
+──────────────────────────────+
│       RUNTIME / DATA PLANE   │
│                              │
│ Investigate incident INC-42  │
│ Execute authorized tool reads│
│ Produce investigation result │
+──────────────────────────────+

For example:

  • Control plane defines that the Checkout API assistant may use approved read-only monitoring tools.
  • Data plane executes the permitted metrics request when the engineer investigates INC-42.

Important: Central governance does not replace authorization in the business system. The monitoring service must still enforce its own access rules.

For our local mock, we do not need two independently deployed planes. We only need to understand the separation of responsibilities.

6. Observability versus evaluation

An enterprise assistant must be both operationally reliable and useful.

These are different concerns.

ConceptQuestionINC-42 example
ObservabilityWhat happened during execution?Which tool was called? Did it fail? How long did it take?
EvaluationDid the assistant produce a good result?Did it cite the right evidence? Did it invent a root cause?

A request can complete successfully at the software level and still produce a bad investigation.

For example, all tools might return successfully, but the assistant could recommend restarting the wrong service.

We will eventually measure task success, grounding accuracy, latency, tool errors and cost.

For now, recording tool outputs and checking that every cited evidence ID exists is enough.

This distinction is part of the #73 reference's Stage 2 foundation.

MCP becomes valuable when tools/resources need a reusable host-to-server interface. It can expose reusable tools to compatible AI clients.

A2A is useful for delegating work between independently deployed/operating agents.

AG-UI streams agent state to owned frontends.

A2UI specifies trusted components declaratively.

MCP Apps embeds UI in a compatible host.

These are separate boundaries, not substitutes for one another. None are required just because an application uses an LLM.

We will revisit them when a specific requirement makes the additional complexity worthwhile.

Stage 2 summary

Our initial approach is now clearer:

An authorized, read-only application retrieves facts. An LLM interprets those facts. The engineer remains responsible for remediation decisions.
