What we have built so far

We are not designing the entire enterprise platform in one step. Each stage adds only the capabilities justified by INC-42. The platform-wide concerns remain future work.

  • Stage 1 — Problem, actors, priorities and trust boundaries
  • Stage 2 — LLMs, workflows, tool calling and grounding
  • Stage 3 — Two-tool read-only system and typed contracts
  • Stage 4 — Runnable synthetic Python workflow and tests
  • Stage 5A — Bounded model tool selection and enforcement

Central lesson The LLM may explain evidence and propose what to inspect next. **Application

code and business systems** decide what data can be read and what actions can

run. No production write action exists in our current design.

1.1 Business problem

Customers experience slow checkouts, and the IT Operations team receives a severity-2 alert.

Monitoring reports a p95 latency rise from 240 ms to 1,800 ms, while error rate rises from 0.4% to 3.1%. Deployment v2.7.4 occurred at 09:55, shortly before the degradation.

Fictional incident: INC-42 Checkout API is slow [SEV-2]

SignalNormalDuring incident
p95 latency240 ms1,800 ms
Error rate0.4%3.1%
Deployment—v2.7.4 at 09:55

Illustrative observations:

  • Latency is near normal around 09:45.
  • Deployment v2.7.4 occurs at 09:55.
  • Latency increases sharply afterward, reaching 1,800 ms around 10:10.
  • Temporal correlation does not prove the deployment caused the slowdown.

Do not confuse correlation with cause A deployment near the incident is a lead for investigation, not proof that the deployment caused the slowdown.

The on-call engineer needs to answer:

  • What changed?
  • What evidence explains the slowdown?
  • What is the most likely cause?
  • What should we investigate or do next?
  • Can we safely recover the service?

The on-call engineer currently checks monitoring dashboards, logs, deployments, incident records, and runbooks separately.

The process is slow, repetitive and vulnerable to human error under pressure.

Business objective

Help IT Operations engineers investigate incidents faster, understand evidence, and recommend safe next steps, while retaining human responsibility for remediation.

Desired outcomes include:

  • lower investigation effort,
  • potentially shorter mean time to resolution (MTTR),
  • fewer unsafe operational decisions.

These are goals, not measured improvements.

Current architectural limit

One bounded incident investigator, two read-only tools, synthetic records, an optional model adapter, and no enterprise-scale platform services.

1.2 Representative user request

Investigate incident INC-42. Checkout API latency increased. Find possible causes and recommend the safest next step.

1.2.1 Representative user journey

Our representative request:

"Investigate incident INC-42. Checkout API latency increased. Find possible causes and recommend the safest next step."

  1. Open the incident. The engineer selects INC-42 and begins the investigation.
  2. Verify access. The application checks the engineer's identity and permissions before retrieving protected information.
  3. Collect evidence. The assistant obtains latency measurements, error rates and recent deployment information from approved systems.
  4. Analyze findings. The assistant compares the incident timeline with recent changes and identifies possible explanations.
  5. Present conclusions. It separates confirmed observations from hypotheses, identifies evidence sources and reports missing information.
  6. Attach evidence. The assistant links relevant data sources to the findings.
  7. Recommend next steps. The assistant does not independently change production.
  8. Engineer reviews. The engineer reads the report and decides whether to take action.

Example of the expected response

**Incident investigation — INC-42**                             [Needs review]

**Observed facts**

- Checkout API p95 latency increased from 240 ms to 1,800 ms.   
  Evidence: `METRIC-07`.

- Deployment v2.7.4 occurred shortly before degradation.        
  Evidence: `CHANGE-03`.

**Hypothesis**
The recent deployment may be contributing to the slowdown.
Available evidence does not establish the root cause.

**Recommended next step**
Compare request latency and database connection metrics before and after
deployment.

If findings support a rollback, ask the authorized operator to review that
option.

[No production action executed. Synthetic example output.]

Notice that the result contains observations, a hypothesis and a recommendation. These are three different kinds of information.

A well-designed assistant must not turn a weak hypothesis into a confirmed root cause.

Functional requirements describe what the system must do.

  • P2 — Later: Deferred until requirements justify the complexity.

The model's answer is not a source of operational truth.

1.7 Trust boundaries

  1. A chat request does not grant access to all services.
  2. The API must derive identity and permissions from verified server-side context.
  3. Each data source must enforce its own authorization rules.
  4. Tool responses, logs, documents, and model-generated text are untrusted data, not executable instructions.
  5. A suggested rollback or an approval button is not authorization to perform a rollback.

1.8 First-version scope

Included:

  • One fictional enterprise and IT Operations team.
  • One incident: INC-42, Checkout API.
  • One authorized on-call engineer.
  • Two read-only capabilities: retrieve metrics and deployment history.
  • Evidence-backed findings, uncertainty, and recommendations.
  • Synthetic source data only.

Excluded initially:

  • Automatic restart, rollback, or infrastructure writes.
  • Real credentials or production integrations.
  • Multi-agent delegation, MCP, A2A, RAG, and advanced UI protocols.
  • Global multi-region platform infrastructure.

Explicit assumptions

Working assumptions: The incident has a known tenant and service; the authorized operator may read its records; two sources are enough for the first demonstration; the application has no write permission.

AssumptionReason

One authorized engineer can access the selected evidenceKeeps the first authorization boundary small

Stage 1 result

We defined an investigation copilot, not an autonomous operations controller. Safety, provenance, and ownership take priority over sophistication.
