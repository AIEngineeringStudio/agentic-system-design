1. Minimal component architecture

We will now turn the Stage 1 requirements and Stage 2 concepts into a concrete system design.

Our goal is to build the smallest architecture that can:

  1. Accept an investigation request for INC-42.
  2. Retrieve authorized metrics and deployment evidence.
  3. Use an LLM to analyze the evidence.
  4. Return findings and a safe recommendation.
  5. Never modify production.

One bounded investigation component and two approved read-only tools. No MCP, A2A, RAG or distributed platform services yet.

2. Ownership by component

This distinction is more important than the choice of framework.

Data or decisionOwner
Verified user identityAuthentication system / application
Access to operational recordsSource-system authorization
Metric valuesMonitoring system
Deployment historyDeployment system
Investigation executionInvestigation workflow
Generated explanationLLM output, not authoritative evidence
Production remediationAuthorized operations service and human decision-maker
ComponentOwnsDoes not own
Investigation APIRequest validation and user-context handlingThe original business records
WorkflowExecution order and result stateUser privileges
Read-only adaptersCalls into approved systemsAuthorization grants generated by the model
Source systemsMetrics and deployment truthLLM interpretation
Analysis componentObservations, hypotheses, recommendationsOperational authority
Report validatorOutput shape and citation existenceProof of semantic correctness

The assistant can summarize operational facts, but it cannot make itself the source of truth.

For example, if the LLM reports a deployment time that conflicts with the deployment system, the deployment record wins.

3. Define the API and typed tool contracts

A contract describes the inputs and outputs a component expects.

Contracts let us develop and test components independently. They also reduce the chance that the model receives unexpected data.

For now, these are proposed application-level contracts, not MCP protocol definitions.

Contract A — Investigation API

REQUEST

{
  "incident_id": "INC-42",
  "service": "checkout-api",
  "question": "Why is Checkout API slow?"
}

The request does not supply a trusted user_id, role or tenant. The backend derives these from the authenticated session.

Contract B — Read-only tools

PYTHON TYPE CONTRACTS — ILLUSTRATIVE

from typing import TypedDict


class Principal(TypedDict):
    user_id: str
    tenant_id: str


class MetricsEvidence(TypedDict):
    evidence_id: str
    service: str
    p95_latency_ms: int
    baseline_p95_ms: int
    error_rate_percent: float


class DeploymentEvidence(TypedDict):
    evidence_id: str
    service: str
    version: str
    deployed_at: str


def get_metrics(
        service: str,
        principal: Principal
) -> MetricsEvidence:
    ...


def get_deployments(
        service: str,
        principal: Principal
) -> list[DeploymentEvidence]:
    ...

These describe logical interfaces, not a particular SDK or wire protocol. The mock implementation will add explicit errors, time bounds and validation.

The trusted principal is created by the application, never generated by the LLM.

Contract C — Investigation result

{
  "run_id": "RUN-42",
  "incident_id": "INC-42",
  "status": "needs_review",
  "observations": [
    {
      "text": "Checkout API p95 latency is 1800 ms.",
      "evidence_ids": [
        "METRIC-07"
      ]
    },
    {
      "text": "Version v2.7.4 deployed at 09:55.",
      "evidence_ids": [
        "CHANGE-03"
      ]
    }
  ],
  "hypothesis": {
    "text": "Recent deployment may be related.",
    "evidence_ids": [
      "METRIC-07",
      "CHANGE-03"
    ]
  },
  "next_step": "Investigate latency by deployment version.",
  "action_executed": false
}

Here, needs_review means the investigation has findings for human review. It does not mean the incident has been resolved or that an operational change is authorized.

The validator can check that METRIC-07 and CHANGE-03 really exist in the retrieved evidence. It cannot, by itself, prove that the hypothesis is correct.

5. Trust boundaries and authorization

There are three important boundaries.

BoundaryWhat must happen
User → Investigation APIAuthenticate the caller and verify incident access
Workflow → Source systemsEnforce permitted tool operations and source-level authorization
Retrieved evidence → LLMTreat results as untrusted data and prevent them from becoming instructions

Example: The engineer may be authorized to inspect Checkout API but not the Payroll API.

Even if the LLM requests get_metrics("payroll-api"), the application and monitoring service must deny the unauthorized request.

A prompt saying "only access Checkout API" is not sufficient security.

6. Failure path — monitoring data unavailable

Suppose the monitoring system times out while the deployment tool succeeds.

+----------------------------+
| Investigation starts       |
+----------------------------+
              |
              v
+----------------------------+
| get_metrics                |
| Result: TIMEOUT            |
+----------------------------+
              |
              v
+----------------------------+
| get_deployments            |
| Result: CHANGE-03          |
+----------------------------+
              |
              v
+----------------------------+
| Evidence incomplete        |
| Cannot verify latency      |
+----------------------------+
              |
              v
+----------------------------+
| Return partial findings    |
| No root-cause conclusion   |
+----------------------------+

Expected result:

{
  "run_id": "RUN-42",
  "status": "insufficient_evidence",
  "available_evidence": [
    "CHANGE-03"
  ],
  "missing_evidence": [
    "metrics"
  ],
  "recommendation": "Retry metrics retrieval or investigate manually.",
  "action_executed": false
}

This is a deliberate reliability choice: partial evidence must not become a confident conclusion.

If authorization fails, the workflow must stop before protected data reaches the model. The API must return an access-denied result and must not disclose incident evidence to the model.

7. Baseline execution limits

Keep execution bounded: Our first version has a proposed execution budget:

ControlInitial rule
Tool callsOne metrics read and one deployment-history read
Model callsOne analysis call
Production write toolsNone
Source failureExplicit incomplete-evidence result
Invalid citationsReject or regenerate within a defined budget
RemediationHuman review, outside the initial execution path

These are design choices for the local baseline, not enterprise service limits.

We also do not need autonomous tool selection yet. A fixed workflow is more predictable because we already know which two records to retrieve.

Later, if the assistant needs to decide whether to inspect logs, database connections or deployment changes based on intermediate evidence, we can replace the fixed sequence with a bounded adaptive agent.

Stage 3 summary

We established the smallest useful design:

Engineer → Authorized API → Bounded workflow → Two read-only tools → Evidence → LLM → Validated report

The important architectural decisions are:

  • Source systems own operational truth and enforce data permissions.
  • Application code controls tool execution.
  • The LLM produces explanations and hypotheses, not authorization decisions.
  • Reports must distinguish facts, uncertainty and recommendations.
  • Missing evidence produces an honest incomplete result.
  • No production changes are permitted.
